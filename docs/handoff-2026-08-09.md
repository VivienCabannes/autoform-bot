# Handoff: orchestration, node sizing, and structural detection

Written 2026-08-09. Scope for whoever picks this up next. Everything here is
outside the `/autoform:setup` and blueprint work currently in flight, which is
deliberately excluded so the two efforts do not collide.

Source: field report from Patrick Hulin, who formalized an LLM-generated
textbook toward finite flat group schemes with Codex delegating proofs to a Luna
sub-agent. It proved 43 of 65 nodes before getting permanently stuck. His repo
is `https://github.com/phulin/finite-flat`; it is the reproduction case for
most of what follows.

Already addressed, do not redo: the setup scaffold is now deterministic
(`autoform init`, `autoform_cli/scaffold.py`), and worker mutations already run
in a disposable worktree (`autoform_worker/work_units.py:68`) behind
fail-closed Git-ref leases (`autoform_cli/claims.py`).

---

## 1. Nodes are too large and nothing measures them

**Report.** "The agent review step did not detect several instances where nodes
were way too big and needed to be decomposed further. I think 'PR-sized' is a
little too vague; maybe you want to ask the roadmap / agent-review steps to
estimate line counts for everything and then split any that are over a certain
amount?"

**Confirmed.** `autoform_cli/audit.py` has sixteen finding codes and not one is
about size, difficulty, or fan-in:

```
declared-coverage-gap      empty-coverage-contract   formalizable-container
invalid-graph              invalid-lean-root         lean-target-kind-mismatch
lean-target-not-found      mathlib-without-declaration
missing-coverage-contract  missing-declaration-intent
missing-depends-section    missing-lean-target       missing-source-link
missing-statement-text     proof-without-statement   unreadable-coverage-file
```

`skills/roadmap/SKILL.md` says a node is "one pull-request-sized unit" and
"must identify one unique main result". Both are judgment calls with no
measurement behind them, so an agent that misjudges gets no feedback until a
prover fails repeatedly.

**Suggested direction, not a spec.** A pre-formalization size estimate is
guesswork, but a few proxies are cheap and objective: statement length, number
of distinct hypotheses, count of prerequisites, and depth of the proof sketch.
The strongest signal is probably retrospective: once a node has a `lean:`
declaration, its actual line count is knowable, and a corpus of finished nodes
gives a real distribution to flag outliers against. Consider a
`node-likely-too-large` audit finding driven by the authored proxies, and a
separate report over completed work that calibrates the threshold.

Worth deciding first: is this an `audit` finding (deterministic, offline, runs
in CI) or an `agent-review` rubric (judgment, needs a model)? The audit is
where a hard gate belongs; the rubric is where nuance lives. Patrick asked for
the gate.

**Acceptance.** Running the new check over `phulin/finite-flat` flags the nodes
he had to split by hand. Ask him which ones those were; that is the labelled
set and it already exists.

## 2. The orchestrator abandons nodes instead of repairing them

**Report.** "When sub-agents failed to complete a node (usually due to an
incorrect formalization of the statement), the orchestrator decided to just not
formalize those pieces at all. I instructed it to instead try to repair the
statement and continue."

This is the highest-value item on the list. A formalizer that silently drops
what it cannot prove produces a blueprint whose green fraction is not
meaningful, and Patrick only caught it because he was watching.

**Where it lives.** `agents/escalation-triage.md` exists and
`autoform_worker/work_units.py` has `_enqueue_escalation` gated on
`recovery_state.proof_fingerprint`, so there is machinery for "this attempt
failed, record why". What is missing is the loop back to the *statement*: a
failure caused by a wrong formalization needs the article edited, not another
proof attempt against the same wrong target.

**Design question to settle before coding.** Statement repair mutates the
authored blueprint, which is the one artifact the system treats as
human-authored truth. Decide whether an agent may edit a statement
autonomously, only with a human in the loop, or only by opening a PR that a
reviewer must accept. Note `autoform_worker/agent_work.py` currently disables
graph-writing roles entirely, with `WorkerConfig.durable_identity_ready`
hardcoded `False` and a docstring saying roadmap curation "remains disabled
until graph-writing roles are rewritten to edit canonical Markdown articles and
durable article identity is approved". That decision is a prerequisite for this
work, not a detail of it.

**Acceptance.** A node whose Lean statement does not match its source is
detected as a *statement* failure rather than a proof failure, and the run ends
with it either repaired or explicitly parked with a reason. Nothing is silently
skipped.

## 3. Parallel agents in one checkout

**Report.** "I think there is some infrastructure needed around cooperation in a
single worktree. The agents seemed to get confused as to how to deal with builds
and edits running in parallel (or maybe I'm supposed to be using one worktree
per agent)."

**Partly addressed.** Two pieces already exist:

- `autoform_worker/work_units.py:68` `_isolated_worktree` runs every mutating
  unit in a disposable worktree, "never in the operator's checkout"
  (`do_review:344`, `do_prove:237`, `do_fixlike:498`, `do_progress:601`).
- `autoform_cli/claims.py` gives fail-closed compare-and-swap leases under
  `refs/autoform-claims/`, and as of 2026-08-09 `skills/orchestrate/SKILL.md`
  instructs host agents to acquire, renew, and release one.

**What is left.** Both of those cover the *Python worker fleet* and, now, an
agent that reads the Orchestrate skill. Patrick was driving Codex with a Luna
sub-agent, which is neither. Two gaps:

- Nothing serializes `lake build`. Concurrent builds in sibling worktrees
  contend on the same `.lake` cache and on elan; that is likely what he saw.
- The claim protocol is advisory for host agents. It is documented, not
  enforced; an agent that ignores it collides silently.

**Suggested direction.** Answer his actual question in the documentation first:
one worktree per agent, or one shared checkout with a build lock? Pick one and
say so, because right now the honest answer is "it depends on which entry point
you used". Then make the chosen model enforceable rather than advisory.

## 4. Structural detection for hand-built and legacy vaults

Not from Patrick's list directly, but it is the root cause of his first report
and it survives the `autoform init` fix.

`phulin/finite-flat` wrote chapter pages as siblings of their directories
(`03-finite-etale-galois.md` next to `03-etale-galois/`) with no
`<chapter>/README.md`. Reproduce it:

```bash
git clone --depth 1 https://github.com/phulin/finite-flat /tmp/ff
find /tmp/ff/blueprint/roadmap -name '*.md' -exec sed -i '' -E '/^(kind|status):/d' {} +
autoform check /tmp/ff/blueprint
```

That prints `OK: 72 articles, 125 dependencies`. It is green, and yet:

```
03-etale-galois/splitting        parent='roadmap'  depth=1
03-finite-etale-galois           parent='roadmap'  depth=1
root children: 71 of 72
```

Seventy-one of seventy-two articles hang directly off the root. There are no
chapters, so the published book has no structure. `autoform init` prevents this
for new projects; nothing detects it in a vault built by hand, by an older
Autoform, or by an agent that went off-script anyway.

**Suggested checks.** A roadmap directory containing `.md` files but no
`README.md`. A root article with an implausible number of direct children. Both
are cheap, deterministic, and belong in `audit.py`.

**Note for whoever contacts Patrick.** The `sed` above is not incidental. The
`kind` and `status` frontmatter keys were removed on 2026-08-09 (`c095b5d`), so
his repo now fails `autoform check` with one hard error per page until he runs
it. Send him that command.

## 5. Smaller known defects, unowned

- **`autoform_worker/constants.py`** has no `^blueprint/` entry in
  `_MERGE_PATH_ALLOW`, and `autoform_worker/survey.py:483` gates PR auto-merge
  on it. Any PR touching the now-authoritative roadmap can never auto-merge.
  One line. `origin/integration` has the fix.
- **`scripts/lint_plugin.py`** enforces a four-command surface
  (`PUBLIC_WORKFLOW_SKILLS`) while the tree ships seven skills, so
  `deicyde/main` CI's `quality` job is red. Whether the answer is to widen the
  linter or narrow the surface is a product decision; the repo currently
  disagrees with itself, since the Muse manifest and the Codex `defaultPrompt`
  both list seven. It also has a regex bug: a cross-skill link
  `../setup/references/zulip.md` is misread as
  `skills/roadmap/references/zulip.md`.
- **`./autoform`** at the repository root is a run-from-checkout shim that
  dispatches to `autoform_worker.cli`, but the installed `autoform` console
  script is the blueprint CLI as of the 2026-08-09 rename. Same command, two
  programs, depending on install method. Rename the shim to `./autoform-worker`
  and fix its docstring.

## 6. Framing question worth raising with the team

Patrick: "I'm most interested in fully-automated formalization, so I haven't
been doing any human review. Maybe that means I'm just not using the project
the way you all intended."

He is describing a real usage mode the skill surface does not name. `setup`,
`roadmap`, `orchestrate`, and `evaluate` are all agent-drivable, and
`human-review` is optional, so unattended operation is supported in practice
but nowhere endorsed. If it is a mode we intend to support, it should be stated,
and the guarantees that hold without a human should be spelled out: what CI
verifies, what a claim proves, and what nothing checks.
